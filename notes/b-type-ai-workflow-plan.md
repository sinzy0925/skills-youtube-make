# 就労支援B × AI効率化・仕組み化メモ

作成日: 2026-08-26  
元会話: Cursor チャット（skills-youtube-make）  
目的: 在宅の就労継続支援B型で受けた仕事を、AI・スキル・アプリで効率化し、可能なら他者へ引き継げる形にする構想の整理

---

## 0. 危険部分（厳しめレビュー要約）

思想としては筋が通っている。ただし **実行前に酔ると壊れやすい点** だけ先に置く。

1. **仕事を見る前に解がある**  
   定型データ作業前提。B型の実仕事が「少しずつ違う依頼」や目視中心なら、パイプラインの大半は使えない。仮説のまま勝ち確にしない。

2. **「きつくない」＝仕組み化しやすい、ではない**  
   楽な仕事ほど、アプリ化の初期コストが工賃・評価に見合わないことがある。設計遊びで時間を溶かす失敗が最も起きやすい。

3. **配布先前提が重い**  
   Cursor・スキル・リポジトリは「あなたの環境では簡単」。他利用者が同じスタックを持たないなら、第1形態は共有手順や1クリック実行の方が正しい。

4. **「人付き合いが減る」は自己欺瞞になりうる**  
   許可取り・説明・問い合わせ・失敗時対応で、最初は対人が増える。減るのは感情労働で、調整コストは前倒し増。ここで場を壊しやすい。

5. **品質責任が曖昧なまま美談化しない**  
   自動化ミスの納品事故時、仕組み作成者に火が飛ぶ。事業所公式の最終確認者を決める前に「置いてきぼりを出さない」を名乗らない。

6. **メタスキルは尚早**  
   仕事ゼロで抽象ツールを厚くしない。手作業1本 → スクリプト1本 → 薄い手順、のあと。メタスキルは複数本回ってから。

7. **記事との接続を盛りすぎない**  
   製造業DXの分断とB型の作業配布は別物。一次情報になるのは回した後だけ。

8. **成功条件を先に置く**  
   例: 同種仕事が月N回以上、1件あたり手作業X分以上、など。回収できない自動化はしない。

運用ルール: **仕事Aが来るまで、このメモ以上に体系を増やさない。**

---

## 1. 前提・動機

### 状況
- 障害者として **就労継続支援B型（就労支援B）** で仕事を受ける予定
- **在宅ワーク**
- そこで得た仕事を、うまく **AIで効率化**したい

### なぜB型か
- 以前はクラウドワークスでも同様に自動化していた
- クラウドワークスは怪しい案件が多く、やめた
- B型は事業所経由で発注元・作業内容・納品ルールが見えやすく、**安心できる場**として選んだ

### 想定
- 障害者向け・在宅のため、極端にきつい仕事は少ない想定
- だからこそ、作業そのものより **仕組み化・引き継ぎ** に価値が出やすい
- うまく型にできれば、他の人に渡せる可能性がある

### 期待する感覚
- 「暇だな〜」が減り、得意な設計・検証で手応えが出ると楽しいかもしれない
- 面倒な人付き合いの泥沼より、仕組みを作って渡す側に寄れる

---

## 2. 目指す姿（一文）

得意な分野（見極め・アプリ化・スキル設計）で輝きつつ、  
他の人は「スキル実行 → 結果確認」だけで参加できるようにし、  
**組織を壊さず、置いてきぼりを出さない**働き方を小さく実証する。

---

## 3. 参考にした気づき（Zenn記事との関係）

参考記事の趣旨（要約）:
- AIで個人生産性が上がると、レビュー・定着・共通言語が追いつかずチームが置いていかれる
- 悪意より構造で分断が起きる
- 説明書を書いても読まれない、という定着の失敗も起きうる

### 記事の壊し方（避けたい側）
- 速い人だけが先に行く
- 分かっている側が、分かっていない側の感情・時間まで抱え込む
- 説明書が増えても読まれず、現場が動かない

### こちらの裏返し（やりたい側）
- 難しい判断とアプリ化を先に引き受ける
- 他の人には **実行できる形** で渡す
- 学習を「長い説明書を読む」から「実行して結果を見る」に変える
- 差を隠すのではなく、**参加できる工程に落とす**

## 4. コアとなるパイプライン

理想フロー:

```
仕事Aを受ける
  → 内容を見て「こんなアプリが必要」と判断
  → 仕事Aを元に「アプリ化用スキル」を作らせる
  → そのスキルで仕事Aをアプリ化する
  → 薄いスキルをリポジトリに残す
  → 指示は「このスキルを使い、アプリを実行し、結果が正しいか確認して」
```

### 各ステップの意味

| ステップ | やること | 誰向き |
|---------|---------|--------|
| 受注 | 仕事Aの仕様・入出力・例外を把握 | 自分（初期） |
| 可否判断 | 定型か／アプリ化価値があるか | 自分 |
| アプリ化スキル作成 | Cursor等で「仕事A用の作り方スキル」を生成 | 自分＋AI |
| アプリ化 | スクリプト／アプリ本体を実装 | 自分＋AI |
| 薄いスキル残置 | 実行手順＋確認手順だけ残す | リポジトリ |
| 運用 | スキル実行 → 結果レビュー | 自分 or 配布先 |
| 改善 | ダメならPDCA | 自分中心 |

### トークン・運用上の狙い
- 毎回AIに長い手順を考えさせない
- 定型はアプリに寄せ、スキルは **実行方法と確認** に薄くする
- 既存の思想「スキルをアプリ化してトークン消費を抑える」と同じ型

---

## 5. リポジトリ構成のイメージ

```
job-a/
  .cursor/skills/run-job-a/SKILL.md   # 実行＋確認だけ（薄い）
  app/                                # 本体（スクリプト／アプリ）
  samples/                            # 入力例・正解例
  checks/                             # 自動検証（任意）
  README.md                           # 人が読む引き継ぎ（最小）
```

### 配布時に渡すもの
- スキル（呼び方・実行・確認の指示）
- アプリ／スクリプト
- サンプル（正解の見本）
- 短いFAQ（よくあるエラー）

### 渡さない／後回しでよいもの
- 長い概念説明だけのマニュアル（読まれない前提）
- アプリ化の設計議論ログ全部

---

## 6. 「説明書を読まない問題」への答え

記事にあった「説明書を書いても誰も読まなかった」に対して:

- スキル＋アプリなら、他者に求める行動を  
  **「実行して、結果をレビューする」** に圧縮できる可能性がある
- 学習コストは下がるが、**簡単＝確認不要** ではない

### 残る必須スキル（配布先）
1. 環境が動くこと（PC、必要なランタイム、Cursor等）
2. スキルの呼び方が分かること
3. **結果の良し悪しを見る目**があること

---

## 7. 検証（結果確認）の設計

アプリ化できる部分は、バグとエラーがなければ基本OKになりやすい。  
それでも **結果を確認するロジックは必要**。

### 2層の確認

| 層 | 内容 | 自動化しやすい例 |
|----|------|------------------|
| 1. 動かした確認 | 落ちない、成果物が出る、件数がある | exit code、ファイル存在、行数 |
| 2. 中身の確認 | 仕様どおりか、抜け・ズレ・誤変換がないか | 必須項目、形式、差分、ルールチェック |

### 3点セットで設計する
1. **アプリ化**（定型処理）
2. **検証ロジック**（ルール化できる検査）
3. **人が見る箇所**（判断が残る部分）

検証手順までスキルに書いておくと、配布後の品質がブレにくい。

---

## 8. 役割の正体（PMではない）

近いが、通常のPMとは違う。

### PM寄り
- 仕事の切り方を決める
- 他の人に渡せる形にする
- 品質と進め方を見る

### 違う点
- 会議・調整・進捗管理が主ではない
- 本体は **仕組みを作る人**（アプリ化・スキル設計）
- 人を動かすより、**人が動けるレールを敷く**

### 近い呼び方
- テックリード（小規模）
- 業務改善／仕組み担当
- イネーブルメント（他の人が働けるようにする人）

### 自分にとっての利点
- 面倒な人付き合いの総量が減りやすい
- 得意なことをやって、うまくいけばOK
- ダメならPDCAで直せる（人間関係の泥沼より改善サイクル向き）

※ 付き合いがゼロにはならない。最初の許可取りと、配布後の短いフィードバックは残る。

## 9. 発展形：自分は初期担当、他者に配布

### アイデア
- B型で、自分が初期の仕事を受ける
- アプリ化できるか判断する
- 可能ならアプリ化する
- スキル＋アプリを他の人に配布して作業してもらう

### 向いている理由
- 見極めとアプリ化は難易度が高め → 得意を活かせる
- 他の人は実行と確認で参加できる
- 事業所には「属人作業の削減／立ち上がり高速化」と説明しやすい

### 制約・リスク
- **事業所の許可が前提**（外部ツール、AI、配布）
- 配布後に問い合わせが自分に集中しやすい → FAQが必要
- 配布先のPC環境・リテラシー差で「同じでも動かない」が起きる
- 品質責任の所在を決める必要がある（誰が最終確認するか）

### 現実的な始め方（段階）
1. 自分が1種類だけアプリ化して安定運用する
2. 支援員に「同じ作業を他の人にも渡せる形にしました」と見せる
3. 希望者1人に試験配布する
4. うまくいったら役割として定着させる

最初から「配布係」を名乗らなくてよい。

---

## 10. 安全に始めるための原則

1. **事業所のルールを先に確認**  
   AI利用・外部ツール・納品物の扱い・他者への共有がOKか
2. **1種類の仕事だけ測る**  
   手作業時間 vs AI／アプリありの時間
3. **品質ゲートを残す**  
   最終確認は自分または決められた確認者
4. **効いた手順だけスキル／アプリ化**  
   全部自動化しない。定型だけ切る
5. **「楽をする」より「ミスと所要時間を減らす」** と説明できる形にする

### アプリ化してよいもの／よくないもの

| 向き | 例 |
|------|----|
| 向く | 繰り返し、入出力が明確、例外が少ない、正解例がある |
| 向かない | 毎回判断が大きく変わる、仕様が曖昧、対人調整が本体 |

- 正当な仕事用途のPC購入として設計する方が安全
- 障害年金・B型工賃・事業所得の組み合わせは個別確認が必要（市区町村／税理士）

## 12. 成功イメージ（記事の裏返し）

障害の有無にかかわらず:

- 「全部を理解して作れる人」と
- 「手順どおり実行・確認できる人」

を分ける。

速い側が組織を壊すのではなく、  
**速い側がレールを敷き、続く側が走れる**ようにする。

B型の小さな現場でこれが回れば、一般論の感想より強い一次情報になる。

## 13. 次にやること（仕事が来るまで／来てから）

### 今（仕事前）
- [ ] 構想をこのメモで共有できる状態にする（本ファイル）
- [ ] 事業所のAI・ツール・共有ルールを確認する質問リストを作る
- [ ] （任意）「受注→アプリ化スキル生成」用のメタスキル要件を下書きする

### 仕事Aが来たら
- [ ] 入出力・例外・正解例を1枚に書く
- [ ] アプリ化可否を判断する
- [ ] 可能ならパイプラインどおりアプリ化＋薄いスキル化
- [ ] 自動検証できるところまで載せる
- [ ] 自分で安定運用 → 必要なら試験配布

### やらないこと（初期）
- 全業務の一気アプリ化
- 許可前の外部配布
- 確認工程の省略
- 説明書だけの引き継ぎ

## 14. 事業所確認用・質問リスト（案）

- AI（ChatGPT / Cursor 等）の利用は可能か
- 自分のPC・自作スクリプトの利用は可能か
- 成果物の生成過程（AI利用）を報告する必要があるか
- 同じ作業手順を他の利用者へ共有してよいか
- 品質の最終確認者は誰か
- 禁止ツール・禁止サイトはあるか
- 個人情報・機密の取り扱いルールは何か

## 15. メタスキル化する場合の要件メモ（将来）

名前案: `job-to-app-skill` など

入力:
- 仕事Aの説明、サンプル入出力、納品ルール、制約

出力:
1. アプリ化可否判断レポート
2. アプリ仕様（入出力、例外、非対象）
3. 実装（app/）
4. 自動チェック（できる範囲）
5. 運用用の薄い SKILL.md（実行＋確認）
6. 配布用 README（最短手順）

ゲート:
- 不可なら「手作業手順＋チェックリスト」だけ出して終了
- 可なら実装後、サンプルで検証が通るまで完了扱いにしない

## 16. まとめ

- B型の在宅仕事を、安心できる場として受け、AIで効率化する
- 型は「受注 → 可否判断 → アプリ化 → 薄いスキルで実行・確認」
- 説明書依存を減らし、実行とレビューに寄せる
- 検証ロジックは必須（動いた確認＋中身の確認）
- 役割はPMより「仕組み担当／イネーブルメント」
- 発展形は他者へのスキル＋アプリ配布（許可と段階導入が前提）
- 記事の分断を反面教師に、得意で輝きつつ置いてきぼりを出さない
